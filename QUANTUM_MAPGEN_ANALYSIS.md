```
Type: Soft constraint / optimization objective
Variables: Item positions relative to cover positions

Weight in energy: 5.0
```


### 1.4 Current Limitations & Pain Points

1. **WFC contradiction rate at scale**: 128×128 grids risk contradiction with no backtracking. Fallback produces trivial layouts. This is the biggest quality bottleneck.

2. **SA convergence with many items**: 25 items with strict spacing (up to 50m for sniper) on small maps can make feasible initialization difficult. The initializer caps at 2000 attempts per item type.

3. **Disconnected C#/Python stacks**: The production C# build pipeline (mapgen-environment) has stub WFC/Voronoi, while the Python implementations are full but not directly consumed by Unity.

4. **Quality gate retry loop**: The orchestrator retries up to 3 times with different seeds if quality < 0.6. This is a brute-force approach — no learning between attempts.

5. **Constraint conflicts**: Spawn balance (items should be equidistant from spawns → center tendency) conflicts with risk/reward (powerful items should be exposed → edge tendency). The SA resolves this by weight balancing, but local minima are common.

6. **Missing NavMesh-based analysis**: Full path-length-based flow analysis (via Unity NavMesh) is stubbed out in C#. The Python version uses grid-based NetworkX graphs which approximate but don't account for 3D geometry, ramps, or jump pads.

## Phase 2: Simulated Annealing Deep Dive

### 2.1 SA Implementation Analysis

**Solution representation:**
Dictionary mapping item type (string) → list of 2D positions (float tuples).
Each position is a (x, z) coordinate on the walkable grid.
Total variables: 9 item types, 25 individual items, each with 2 continuous coordinates.

**Energy/cost function (exact):**
```python
E = 10.0 * spawn_balance    # σ of per-spawn advantage scores
  +  5.0 * risk_reward       # exposure/cover penalties per item
  +  3.0 * flow_alignment    # choke proximity penalties
  +  7.0 * spacing_penalty   # pairwise min-distance violations
  +  4.0 * strategic_depth   # power-item centroid offset from center
```

Individual terms:

| Term | Computation | Range |
|------|-------------|-------|
| `spawn_balance` | For each spawn, sum(value_i / (min_dist_to_item_i + 1)). Return std dev across spawns. | 0 — ~5.0 |
| `risk_reward` | Per item: if prefer_exposed and closest cover < 10m → penalty 2*(10-d). If prefer_cover and closest cover > 15m → penalty (d-15). | 0 — ~40.0 |
| `flow_alignment` | Per item: if closest choke < 5m → penalty 3*(5-d). If closest choke > 15m → penalty 0.5*(d-15). | 0 — ~30.0 |
| `spacing_penalty` | For all pairs: if dist < max(min_spacing_a, min_spacing_b) → penalty 5*(required-actual). | 0 — ~200+ |
| `strategic_depth` | Centroid of {sniper, rocket, heavy_armor} positions. Penalty = max(0, dist_from_center - 30). | 0 — ~20.0 |

**Neighborhood function:**
1. Pick random item type (that has placed items)
2. Pick random item index within that type
3. Find walkable candidates within 25m of current position (local refinement)
4. Pick random candidate from nearby
5. Check spacing against all other items (excluding the moved one)
6. If spacing OK → accept move; otherwise → keep original position
→ This is a **single-item local swap** neighborhood.

**Cooling schedule:**
Exponential: `T = T * 0.95` per iteration.
Start: T=1000 → After 100 iters: T≈5.92 → After 200 iters: T≈0.035 → stops.
Effective iterations: ~160-200 before temperature drops below threshold.

**Convergence behavior:**
- With 25 items on a 64×64 grid, the SA typically finds a good solution within 150-300 accepted moves.
- The cooling rate of 0.95 is aggressive — the system cools fast, limiting exploration.
- Local minima are a concern for spawn balance when spawn points are asymmetric.
- The C# version (cooling=0.96, T=750, 4500 max iters) allows slightly more exploration.

**Solution quality variance:**
Moderate. Running with different seeds produces noticeably different placements, especially for the 6 health_small items which have the weakest constraints. Power items (sniper, rocket) tend to converge to similar positions across runs due to strong constraints.

### 2.2 QUBO Feasibility Assessment

```
Constraint: C-001 (Spawn Balance)
QUBO-convertible: Likely
Reasoning: Std dev of advantage scores is not directly quadratic, but can be
  approximated by minimizing pairwise differences: Σ(advantage_i - advantage_j)².
  Each advantage_i is a linear sum over placement variables, making the pairwise
  difference quadratic. Requires precomputing distance from each candidate position
  to each spawn.
Variable count estimate: N_items × N_candidates binary variables
Interaction density: Medium (cross-spawn interactions)
```

```
Constraint: C-002 (Risk/Reward)
QUBO-convertible: Yes
Reasoning: For each item i at candidate j, the cover distance is precomputable.
  The penalty is a function of a single variable x_{i,j}, making it a linear
  (diagonal) QUBO term. No quadratic interactions needed.
Variable count estimate: Adds to diagonal terms only
Interaction density: Sparse (linear terms)
```

```
Constraint: C-003 (Flow Alignment)
QUBO-convertible: Yes
Reasoning: Same structure as C-002 — choke distance from each candidate position
  is precomputable. Penalty is per-variable (linear QUBO term).
Variable count estimate: Adds to diagonal terms only
Interaction density: Sparse (linear terms)
```

```
Constraint: C-004 (Minimum Spacing)
QUBO-convertible: Yes — this is the NATURAL QUBO constraint
Reasoning: Penalty when two items are too close is exactly a quadratic interaction:
  penalty * x_{i,j} * x_{k,l} when dist(j,l) < min_spacing. This maps directly
  to the J_ij coupling terms in an Ising/QUBO formulation.
Variable count estimate: O(N_items² × N_candidates²) potential couplings,
  but only non-zero when dist < max spacing (50m), so sparse for large grids.
Interaction density: Medium-to-Dense (depends on grid resolution vs spacing)
```

```
Constraint: C-005 (Strategic Depth)
QUBO-convertible: Likely (with linearization)
Reasoning: The centroid is a linear function of placement variables. Distance from
  center requires a norm, which is quadratic. The max(0, offset-30) is piecewise
  linear. Can be encoded as a quadratic penalty on centroid displacement.
Variable count estimate: Adds O(N_power_items²) quadratic terms
Interaction density: Sparse (only 3 item types interact)
```

```
Constraint: C-006 (Walkability)
QUBO-convertible: Yes (by construction)
Reasoning: Only include walkable positions as candidates. No QUBO term needed.
Variable count estimate: 0 (structural)
Interaction density: N/A
```

```
Constraint: C-007 (Item Counts — One-hot)
QUBO-convertible: Yes — standard QUBO technique
Reasoning: For each item i: (Σ_j x_{i,j} - 1)² = 0 enforces exactly one
  position selected. Expands to: Σ_j x_{i,j} - 2*Σ_{j<k} x_{i,j}*x_{i,k} + 1.
  This is the classic one-hot encoding penalty.
Variable count estimate: O(N_items × N_candidates²) quadratic terms per item
Interaction density: Dense within each item's candidate set
```

| Stage | Input | Output | Runs On | Latency |
|-------|-------|--------|---------|---------|
| QUBO Encoder | walkable mask, spawn/choke/cover positions, item rules | QUBO dict {(i,j): weight} | Local Python | <1s |
| Quantum Solver (simulator) | QUBO matrix | bitstring (binary solution) | Amazon Braket SV1 | 10-60s |
| Quantum Solver (hardware) | QUBO matrix | bitstring (binary solution) | D-Wave Advantage | 1-5s QPU, ~30s total |
| Classical Fallback | same QUBO matrix | bitstring | Local (D-Wave SimulatedAnnealingSampler) | 1-3s |
| Solution Decoder | bitstring + item/candidate mapping | Dict[item_type → positions] | Local Python | <0.1s |

**Fallback strategy:** If quantum solver fails (timeout, infeasible embedding, or all-zeros solution), automatically route to D-Wave Ocean's `SimulatedAnnealingSampler` which solves the same QUBO classically. This ensures the pipeline never blocks.

### 3.2 QUBO Encoding Module Specification

```python
# qubo_encoder.py — Core QUBO formulation

class MapGenQUBOEncoder:
    """Converts MapGen placement constraints into QUBO format."""

    def __init__(self, walkable_mask, spawn_points, choke_points, cover_positions, item_rules):
        self.candidates = self._sample_candidates(walkable_mask, stride=4)
        self.spawns = spawn_points
        self.chokes = choke_points
        self.covers = cover_positions
        self.rules = item_rules

        # Precompute distance matrices
        self.dist_matrix = self._pairwise_distances(self.candidates)
        self.spawn_dists = self._point_to_candidates(self.spawns)
        self.choke_dists = self._point_to_candidates(self.chokes)
        self.cover_dists = self._point_to_candidates(self.covers)

    def encode(self, penalty_strength=100.0):
        """Returns QUBO as dict {(i,j): weight} compatible with both Ocean and Braket."""
        Q = {}

        # Variable mapping: x_{item_idx, candidate_idx}
        # Flattened index: var = item_idx * N_candidates + candidate_idx

        # 1. One-hot constraints (C-007): each item placed exactly once
        self._add_one_hot(Q, penalty_strength)

        # 2. Spacing penalty (C-004): quadratic interaction between items
        self._add_spacing(Q, weight=7.0)

        # 3. Spawn balance (C-001): quadratic pairwise advantage differences
        self._add_spawn_balance(Q, weight=10.0)

        # 4. Risk/Reward (C-002): linear (diagonal) terms
        self._add_risk_reward(Q, weight=5.0)

        # 5. Flow alignment (C-003): linear (diagonal) terms
        self._add_flow_alignment(Q, weight=3.0)

        # 6. Strategic depth (C-005): quadratic centroid terms
        self._add_strategic_depth(Q, weight=4.0)

        return Q

    def decode(self, bitstring):
        """Converts QUBO solution bitstring back to item→position mapping."""
        placement = {}
        n_cands = len(self.candidates)
        for item_idx, (item_type, rule) in enumerate(self.rules.items()):
            for copy in range(rule['count']):
                flat_item = (item_idx * rule['count'] + copy)
                start = flat_item * n_cands
                selected = [j for j in range(n_cands) if bitstring[start + j] == 1]
                if selected:
                    pos = self.candidates[selected[0]]
                    placement.setdefault(item_type, []).append(pos)
        return placement

    def validate(self, Q, classical_sa_result):
        """Checks that QUBO energy at classical solution matches SA score."""
        bitstring = self._encode_solution(classical_sa_result)
        qubo_energy = sum(Q.get((i,j), 0) * bitstring[i] * bitstring[j]
                         for i in range(len(bitstring))
                         for j in range(i, len(bitstring)))
        sa_score = self._compute_sa_score(classical_sa_result)
        return {'qubo_energy': qubo_energy, 'sa_score': sa_score,
                'correlation': 'valid' if abs(qubo_energy - sa_score) < sa_score * 0.1 else 'divergent'}
```

## Phase 4: D-Wave LaunchPad Application Brief

### 4.1 Problem Statement

Procedural map generation for multiplayer FPS games is fundamentally a constraint satisfaction and optimization problem. Our system generates playable arena maps for UberStrike by placing gameplay items (weapons, health, armor, ammo — 25 items across 9 types) on procedurally generated layouts. The placement must simultaneously satisfy:

- **Spawn balance** (equal item accessibility from all spawn points)
- **Minimum spacing** (per-type distance constraints from 8m to 50m)
- **Risk/reward exposure** (powerful items in dangerous positions)
- **Flow alignment** (items positioned relative to choke points)
- **Strategic depth** (power items distributed around map center)

We currently solve this using **classical Simulated Annealing** — the direct classical analog of quantum annealing. Our SA optimizer runs 7,500 iterations with exponential cooling (T₀=1000, α=0.95) and produces good-but-not-optimal solutions with noticeable variance across runs. We want to test whether D-Wave's quantum annealer finds better solutions or explores the solution space more effectively.

### 4.2 Technical Approach

**QUBO formulation:** We encode item placement as binary variables x_{i,j} (item i at candidate position j), with:
- One-hot constraints ensuring each item is placed exactly once
- Quadratic penalty terms for spacing violations (natural QUBO fit)
- Linear terms for risk/reward and flow alignment (precomputed distances)
- Quadratic terms for spawn balance (pairwise advantage differences)

**Problem size:** 25 items × 50-150 candidate positions = 1,250-3,750 binary variables, well within D-Wave Advantage's 5,000+ qubit capacity.

**Comparison methodology:** Identical constraint formulation run through three solvers:
1. Classical SA (our current production optimizer)
2. D-Wave quantum annealer (QPU)
3. D-Wave hybrid solver (LeapHybridSampler)

Metrics: solution energy, feasibility rate, time-to-solution, variance across 100+ runs.

## Appendix A: QUBO Formulation Details

### Variable Encoding

For item type `t` with count `c_t` and `N` candidate positions:

```
Variables: x_{t,k,j} ∈ {0,1}
  t = item type index (0..8 for 9 types)
  k = copy index (0..c_t-1)
  j = candidate position index (0..N-1)

x_{t,k,j} = 1 means "the k-th copy of item type t is placed at candidate j"
```

Total variables: Σ(c_t × N) = 25 × N

### QUBO Terms

**One-hot (for each item copy):**
```
H_onehot = A × Σ_{t,k} (Σ_j x_{t,k,j} - 1)²
         = A × Σ_{t,k} (Σ_j x²_{t,k,j} - 2 Σ_{j<l} x_{t,k,j} x_{t,k,l} + 1)
```
Since x² = x for binary variables:
```
Diagonal: A × Σ_{t,k,j} x_{t,k,j}     (linear terms, +A on diagonal)
Quadratic: -2A × Σ_{t,k} Σ_{j<l} x_{t,k,j} x_{t,k,l}
```
A should be large enough to dominate (A ≥ 100).

**Spacing penalty:**
```
H_spacing = 7.0 × Σ_{(t1,k1)≠(t2,k2)} Σ_{j,l: dist(j,l) < max_spacing}
            max(0, min_spacing - dist(j,l)) × 5 × x_{t1,k1,j} × x_{t2,k2,l}
```
This naturally produces quadratic coupling terms.

**Risk/Reward (linear):**
```
H_risk = 5.0 × Σ_{t,k,j} penalty(t, j) × x_{t,k,j}
```
where `penalty(t, j)` is precomputed from candidate j's distance to nearest cover point and item t's preference (prefer_exposed or prefer_cover).

**Flow Alignment (linear):**
```
H_flow = 3.0 × Σ_{t,k,j} choke_penalty(j) × x_{t,k,j}
```
where `choke_penalty(j) = 3*(5-d) if d<5, 0.5*(d-15) if d>15, else 0`.

**Full QUBO:**
```
H = H_onehot + H_spacing + H_risk + H_flow + H_balance + H_depth
```

### Appendix B: Distance Precomputation

All distance-based terms can be precomputed in O(N² + N×S + N×C) where N=candidates, S=spawns, C=choke/cover points. This precomputation runs locally in <1 second for N≤300, making the QUBO construction fast.
